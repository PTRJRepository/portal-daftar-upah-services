  Based on my analysis of the old backend system, I'll now document the key components and their interactions:

  Old Backend Architecture Analysis

  1. Core Components

  Payroll Service (payroll_service.py)
   - Purpose: Main business logic for payroll calculations
   - Key Functions:
     - generate_rows(): Main method that fetches employee data and calculates payroll
     - Calculation methods for various components (Gaji Pokok, Tunjangan, Premi, etc.)
     - BPJS calculations with complex business rules
   - Data Flow: Fetches data from multiple SQL queries and calculates payroll components

  Database Service (database/database.py)
   - Purpose: Handles database connections with connection pooling
   - Features:
     - Connection pooling for performance
     - Retry mechanisms for failed queries
     - Transaction support
     - Query timeout handling

  Employee Repository (employee_repository_db.py)
   - Purpose: Manages employee data retrieval
   - Functionality:
     - Fetches employee details by gang code
     - Handles gang filtering and pagination
     - Joins HR_EMPLOYEE with HR_GANGLN tables

  API Layer (api/payroll.py)
   - Purpose: Exposes payroll data via REST endpoints
   - Key Endpoints:
     - /report - Main payroll data endpoint
     - /headers - Dynamic column headers
     - /columns - Column definitions
     - /divisions - Division codes
     - /gangs - Gang codes
     - /report/aggregate - Summary data
     - /report/division-optimized - Division-wide data

  2. Data Flow Process

  Employee Data Retrieval
   1. EmployeeRepositoryDB.list() fetches employees from database
   2. SQL query joins HR_EMPLOYEE with HR_GANGLN to get gang membership
   3. Results are filtered by gang code if specified

  Payroll Calculation Process
   1. Employee Data: Fetch employee list using EmployeeRepositoryDB
   2. Payrate Data: Query HR_PAYROLL table for PayRate
   3. HK (Hari Kerja) Data: Use get_total_HK_each_Emp.sql query
   4. Cuti Data: Multiple queries for different cuti types (tahunan, sakit, minggu, nasional)
   5. Tunjangan Data: Multiple queries for beras, jabatan, masa kerja, lembur
   6. Premi Data: Static (brondol) and dynamic queries from PR_ADTRANS_ARC and PR_LOOSEFRUIT_ARC
   7. Potongan Data: BPJS, SPSI, PPH21, and dynamic potongan calculations
   8. Final Calculations: Apply business formulas to calculate totals

  3. Key Business Logic

  BPJS Calculation Formula:
   - Base = gaji_pokok_min (config) + masa_kerja_jumlah
   - BPJS Kesehatan Pekerja = Base × 1%
   - BPJS Kesehatan Majikan = Base × 4%
   - BPJS Pensiun Pekerja = Base × 1%
   - BPJS Pensiun Majikan = Base × 2%

  Hari Kerja Calculation:
   - hari_kerja = hk_count - (cuti_tahunan + cuti_sakit + hk_minggu + hk_nasional)

  Gaji Pokok Calculation:
   - gaji_pokok = hari_kerja * payrate (after cuti deductions)
   - jumlah_upah_kotor = (hk_count * payrate) + total_tunjangan + total_premi (before cuti deductions)

  4. Dynamic Headers and Premi

  Dynamic Premi Headers:
   - Queries PR_ADTRANS_ARC table for distinct DocDesc values
   - Filters out excluded keywords (PPH21, SPSI, etc.)
   - Normalizes field names using _normalize_premi_field_name()

  Dynamic Potongan:
   - Similar to premi but for deduction items
   - Must start with "POT" prefix to be included

  5. Configuration and Constants

  Config File (config.json):
   - Database connection settings
   - Constants for BPJS calculations
   - Upah minimum values
   - Different profiles for local/remote connections

  6. Caching Mechanism

  In-Memory Cache:
   - Payrate mappings
   - Premi data caches
   - Cuti data caches
   - 300-second TTL by default

  7. Error Handling & Retries

  Robust Error Handling:
   - Query timeout handling
   - Connection retry mechanisms
   - Graceful degradation for missing data
   - Fallback values for failed calculations

  This analysis provides the foundation for refactoring the backend to maintain the same functionality while potentially improving
  architecture and performance.
